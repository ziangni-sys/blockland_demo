# 路线

范围、进度和遗留都记在这份文件里，不用 GitHub 的 milestone 和 issue。每个里程碑大约是高强度使用 AI 时 2～3 天的工作量。

## 已定的前提
- 平台：先只做桌面浏览器，用 WebGPU（three.js WebGPU 渲染器）。
- 画面：像素风程序化贴图，PBR 留到画面里程碑。
- 界面：先只做中文。
- 性能目标：核显，视距 8～12 区块，60 帧。
- 发布：GitHub Pages 提供固定试玩链接。
- 联机是核心卖点（M1 试玩后确定）：架构按“联机优先”设计，开房间不需要自己架服务器。一个房间先按 4 人设计。
- 不考虑向后兼容（存档、内部接口）：设计不对就一次性重构。

## 每个里程碑的完成标准
1. 有可以直接打开的试玩链接。
2. 无头测试全部通过，并有浏览器冒烟测试。
3. 对抗式审查做到某一轮不再发现中高严重度问题。
4. 新规则写进 DESIGN.md，新踩的坑写进 LESSONS.md。
5. 负责人试玩确认后，才开始下一个里程碑。

## M1 完成情况

对照完成标准：

1. **试玩链接**：有。合并到 `main` 后由 `.github/workflows/pages.yml` 发布到 GitHub Pages。
2. **测试**：M1 合并时是 1697 个无头测试，1695 个通过、2 个跳过（生成预览图的工具入口）；其中 146 个覆盖 ACCEPTANCE.md 的 24 条场景。浏览器冒烟测试 `scripts/e2e-smoke.mjs` 通过。
3. **对抗式审查**：未做到收敛。14 个模块各做了一轮（两名审查者）并修复了发现的问题，但没有再跑一轮来确认“不再发现中高严重度问题”；验收测试没有独立审计；客户端的修复没有复审。这是为了控制花费由负责人决定的；负责人已接受现状，不再补审。
4. **文档**：M1 新增的规则在 DESIGN.md 末尾，新踩的坑在 LESSONS.md 末尾。
5. **负责人试玩**：已确认 M1 基本完成。

与 M1 原定范围的差距：

- 工程与发布：推送时跑测试的 CI 在 `.github/workflows/ci.yml`（不含计时类的性能测试，那些只在本地跑）；浏览器冒烟测试没有接进 CI。
- 玩家与交互：“选取方块”（中键）、第三人称视角（F5）和出生点附近的示例风车船在 M1 合并后补上了，规则见 DESIGN.md 的“放置与挖掘”“视角”“示例风车船”。这三项没有做对抗式审查，由实现者自己写测试（23 个）。之后按负责人的要求把背后视角改成了越肩视角；这一项做了独立审查，审查发现相机会穿墙，避障部分因此重做并再次验证。
- 船：螺旋桨方块能放置、能随船组装，但不产生推力。负责人决定把螺旋桨并入 M3，和机械传动一起设计。

原计划推迟、实际做了的：WebGL2 降级（自动回退，地址加 `#webgl2` 可强制）、英文界面。

已知遗留：

- 把 WebGPU 的画面呈现到真实画布这一步无法在无头环境验证（软件 GPU 设备在首次呈现时丢失）。WebGPU 的着色与几何路径在离屏模式下验证过。
- 性能目标（核显 60 帧）没有在真实硬件上测量。
- 自动存档每次重新编码所有改动过的区块（约 137 个区块时有约 22 毫秒卡顿）。
- 船被挖断或炸断后仍是一个刚体，不会分裂；结构体内部没有重力更新。

## M2 细化

- 结构体落回方块时不产生新的胶连接；区块加载时清理两侧都没有方块的胶。
- 存档版本升到 2，旧存档打不开（有提示，可以删除）。
- 规则在 DESIGN.md 的“连接”和“副手”，场景 25～29 取代了 4、5。

完成情况：

- 1841 个无头测试通过、2 个跳过；浏览器冒烟测试两种配置都通过。

### M2.1 联机地基

目标：单机也走“服务器 + 客户端”，既有的全部验收场景照常通过；联机逻辑能在一个进程里无头测试（1 个服务器、N 个客户端，模拟延迟和丢包）。

实现规格在 [NETCODE.md](NETCODE.md)：消息、每个 tick 的包、区块和结构体的同步、自己角色的预测和校正、意图、带宽、模块布局和测试计划。它由一名设计者起草，两名审阅者分别从“延迟、丢包、乱序”和“是否符合现有代码、带宽算术”两个角度提了 44 条问题后修订。实现顺序是 3 → 4 → 5 → 8 → 6 → 7 → 9（6 要等工作包 2）；浏览器里的游戏在工作包 9 一次切换，之前一直能玩。

### 子 agent 的用法

- 写代码和修问题的子 agent 默认 Opus、`high`。
- 标了“难”的工作包升级到 `xhigh` 或 Fable，并各配一名审查者。
- 其他工作包由实现者自己写测试；每个阶段结束做一次集成审查，而不是每个模块两名审查者加一名修复者。
