# 原型踩过的坑

每条格式：现象 → 原因 / 解法方向。原型经过 4 轮对抗式审查，成立的问题数（去重后）依次是 28 → 14 → 6 → 3，每轮多半是上一轮修复引入的。

## 物理与碰撞
- **船被推穿薄墙** → 弹簧-阻尼接触力的出口方向要偏向"来的那一侧"（朝质心）。否则接触点越过墙的中线后，会从墙的另一面钻出去。
- **船被转子硬推进地形** → 地形接触力有上限，转子推力却是无限的。判定"夹住"后转子就停止施力，让重叠的格子去损毁。
- **能动的船被误判压坏** → "夹住"不能用接触时长或穿透深度来判，因为叶片推着船走时一直在接触。正确条件有两条：
  - 叶片相对船的速度仍然压向接触点；
  - 这个速度方向几乎正对某个顶住船的地形方向。
  
  阈值要用相对值而不是绝对 m/s，否则转得慢的风车永远判不出"夹住"。
- **卡顿的一帧叶片跳进船体** → 转子姿态要在船的物理子步里插值推进，不能整帧推进一次。
- **叶片侧面擦过船时船被猛踢** → 推出方向可以按叶片的相对速度偏向扫掠方向，但力度要按真实重叠深度算，不能把偏向用的罚分算进深度。
- **船被弹飞** → 未加载的区块被当成实心了。物理要冻结，直到结构体覆盖的所有区块都加载完成。
- **船纵倾、横倾过大** → 平移阻力作用在质心，逐点阻力只用来抵抗转动；另外加龙骨横向阻力，防止侧滑。
- **距离判断偏差** → 半径和距离判断要用同一个参考点：船用包围盒中心，转子用轴心，不能拿质心去比。
- **改成 20 TPS 后船穿墙、抖动** → 原型的船物理按约 180 Hz 子步推进（每帧最多 12 步），出口偏向只在穿透不到半格时有效。每个 tick 内必须再分子步，单步位移要远小于半格。
- **船舱里冒出水面** → 船体所在格子里世界的水还在。渲染水面时按船底的脚印把这部分裁掉（原型最多用 16 个矩形），不要真的去删水。

## 携带与实体
- **贴着船游泳被拎上船；潜行走到甲板边缘掉下去** → 站立、推开、附着、挤压的采样点定义不一致，或者有的按世界轴取、有的按结构体局部轴取。四者要统一，而且附着范围要严格小于推开范围。
- **在船上贴墙走被判挤伤** → 世界碰撞按格子中心近似会让人走进墙里。要按真实世界位置判断：自己走进去的，就逐轴退回这一步；原地不动也卡在里面，才是被结构体带进去的。
- **离开甲板仍被拖着走** → 只有脚下是结构体的格子才携带。在空中时检查脚下整列；踩到世界方块立刻脱离。
- **站在行驶的船上被风车误推、误判挤伤** → 推开判定用了上一 tick 的位置。每个 tick 的顺序应该是：先移动结构体，再把被携带的实体同步到新位置，最后做推开和挤压判定。
- **被风车沿船舷推时误判挤伤** → 推开要逐轴移动：某个轴会让身体"新"卡进别的结构体，就不动这个轴；推之前已经存在的重叠不算。
- **站在甲板上被推回去或拽穿甲板** → 推开时不要用"格中心落在别的结构体里就算实心"这种判断。
- **转盘在船上，人掉穿甲板或卡住不动** → 骑手要和父结构体碰撞。被带进父结构体的格子时，先脱离，交给推开逻辑处理，而且不要立刻重新附着。
- **死亡、打开界面、暂停后状态错乱** → 这几个时刻要分别处理：
  - 死亡：脱离结构体、松开舵；
  - 打开界面：把被携带的玩家同步到结构体当前位置；
  - 暂停：甲板上的物品不能掉下去，也不能沿用冻结前的速度。
- **舵手穿过方块** → 舵手也要做"被结构体带进方块"的检查。
- **沉船上不会溺水** → 只有船还能浮起来（质量小于最大排水体积）时，船体范围内的水才算干；密封空腔永远是干的。
- **沙子落到船上悬浮 30 秒后消失** → 下落方块落到结构体上时，直接变成掉落物。
- **生物被挤住** → 先挪到空位。生物没有血量，生存模式下被挤 3 次算死。
- **挪到空位后立刻又被挤** → 候选空位要按 3D 距离排序，并用和推开相同的采样点检查。

## 组装、方块化与胶水
- **TNT 炸掉轴承后风车悬空一直转** → 移除方块有好几条路径（挖掘、爆炸等），要统一挂一个"方块被移除"的钩子，轴承移除时让转子方块化。
- **炸到船上的轴承时叶片幸存，或者风车整个消失** → 先等冲击波处理完所有结构体，再把转子方块化，最后统一重算。船被炸空时如果还挂着别的转子，先不要删船。
- **船上风车坏了，船的帆数、极速、质量不变** → 子转子变化或消失时，父船要重算这些属性。
- **停靠时站在转盘上的人被瞬移** → 方块化前，如果玩家站在要旋转的子结构上，先让他脱离。
- **风车停下后轴心和轴承之间的胶没了** → 原型里启动时这处胶会被清掉，M1 的做法是记下来、停下时还原。M2.0 起胶属于面：只要一侧还有方块（轴承）胶就留着，不再需要特殊处理。
- **船靠上码头后再组装，把码头带走了** → 胶改成“属于面”之后，船带来的露出胶面落在码头方块旁边，两侧都是可涂胶的方块，就连上了。结构体落回方块时，落下的方块和原有方块之间的胶要去掉。
- **胶面的贴花在夜里发光** → 叠加层的材质默认不受光照。画在方块表面上的东西要用和方块一样的光照。
- **胶的存储** → 规范键记在坐标较小的那一格上，再加上轴向。世界和结构体各用一套坐标编码。移动或旋转时，要按映射后的两个端点重新计算键。
- **同种子开新世界，上一局的胶还在** → 新世界要清空所有全局状态。
- **爆炸掉落朝向变体** → 要映射回代表物品。改用方块状态后这个问题自然消失。
- **读档后液体冻在半路** → 待处理的液体 tick 要存档，或者在区块加载时为流动中的液体和玩家改动过的格子重新排程。
- **临时向量被改写** → 全局共享的临时向量会被嵌套调用中途改写。不要共享，或者严格限定在局部使用。

## 测试
- **测试在高负载下超时、游戏时间变慢** → 模拟和渲染帧绑在了一起。模拟必须能无头步进。
- **修复引入回归** → 每次修复后都要做对抗式审查、写复现脚本、跑全量回归。

## M1 重写时新踩的坑

格式同上：现象 → 原因 / 解法方向。都是对抗式审查或验收测试找出来、已经修掉的问题。

### 物理与碰撞
- **贴着码头滑行的船被叶片逐格损毁** → “夹住”只判断了叶片还在压，没判断船能不能滑走。要求叶片自身的运动方向被支撑正面顶住才算。
- **叶片擦过船体时船被踢飞** → 用来偏向推出方向的扫掠量被当成了接触法线。
- **船顶着另一条船时叶片直接穿过** → 夹住判定只认地形支撑。被地形顶住的其他船也要算支撑。
- **长叶片的叶尖一步跨过船体** → 子步数要按叶尖速度自适应。
- **睡在别的船甲板上的船，脚下被拆后悬空** → 支撑物变化时要唤醒它上面的船。
- **实体在地板接缝处被卡住** → 只能沿“暴露面”推出；两个实心格子之间的面不能当接触面。这条规则一开始没有测试保护，删掉它测试也全绿。
- **盒子坐标是无穷大时查询永不结束** → 无效的盒子一律当作空。

### 携带与实体
- **站在空地上被上升的叶尖“挤伤”** → 朝下的推被归类成天花板，只允许竖直推；地面拒绝后直接判了挤压。竖直推被拒绝时要先试法线的水平分量。
- **在甲板上被斜着推，残留一点重叠被判挤伤** → 竖直分量被“地板抬回”抵消时，要把这个轴按被拒绝处理，重新缩放其余的轴。
- **甲板比码头低 0.01 格就上不了岸** → 需要台阶高度。
- **潜行护边在偏航的甲板或转盘上失效** → 护边的支撑判断要在结构体的当前位姿下做。
- **贴着转了 45° 的船体往前游会被抬上船** → 游泳者永远不能附着。

### 结构体
- **补水把一滩水扩成一片水源** → 补水规则要用最小场景验证不会凭空增加水源。
- **世界里的风车在区块边界附近无故停转** → 冻结范围用了包围球的外接正方形，要用真实包围盒。
- **存档写得出、读不回** → 写入和读取的大小限制不一致。
- **界岩能直接放到船上** → 进入结构体的每一条路径（组装、放置、方块化）都要过同一个检查。
- **格子数有上限，内存却没有** → 结构体按包围盒稠密存储，船体分析泛洪整个盒子，网络也发整个盒子；900 块的细长框架盒子可达 2000 万格，几十 MB、分析几秒、网络发不出去。包围盒也要限制（2^21 格），会让盒子变大的每一条路径都要检查。

### 世界
- **出生点附近的熔岩永远不流** → 构造时先加载区块、后把时钟跳到早晨，加载时排好的 tick 永远到不了。时钟要先设；tick 队列要能处理时钟跳变。
- **安静下来的世界读档后水又流动** → 坡度搜索会读 5 格外的格子，但只有相邻 6 格的变化会唤醒它。
- **约 17% 的区块一加载就被标成“已修改”** → 生成的熔岩贴着洞穴空气。
- **洞穴碎成孤立小腔** → 4 格粗网格插值表达不了细隧道。
- **监听器在回调里取消订阅，下一个监听器漏收这次事件** → 监听器列表改成写时复制。
- **光照引擎必须是第一个监听器才正确** → 不要相信回调参数里的旧值，从区块里读。
- **区块卸载后留下“鬼光”** → 区块消失时要重新检查邻居边界上的光。

### 渲染与客户端
- **强力胶在游戏里看不见** → 贴图画在相邻方块内部，被深度测试挡住。
- **离原点远了区块接缝开裂** → GPU 上是 32 位浮点；场景要相对相机附近的整数原点绘制。
- **水面透明度叠加** → 网格化器已经发了正反两份面，渲染器又开了双面。双面由哪一方负责要写进契约。
- **环境光遮蔽比设计的弱一半** → 网格化器和渲染器各套了一次曲线。
- **火把放下去几乎看不到火焰** → 贴图的画法和网格化器的采样窗口对不上。
- **保存失败仍然退出，进度丢失** → 只有保存成功才关闭世界。
- **天空的昼夜和游戏时间不一致** → 客户端自己用世界 tick 算昼夜，没算偏移。只能读模拟层给的时间。
- **某个区块网格化失败，加载界面永远卡住** → 失败的任务也要结案。
- **死亡时按着空格，一松手就重生** → 死亡界面不能自动聚焦重生按钮。
- **无头环境的软件 WebGPU 设备在第一次呈现时丢失** → 初始化时先在临时画布上试着呈现两帧，失败就退回 WebGL2。
- **第三人称相机穿墙** → 避障只沿射线在命中点前留边距，垂直于射线的方向没有留空；相机擦着墙走时射线打不到墙，位置却贴到墙上，近裁剪面切进方块。要把相机当成一个小方块沿路径扫，在各个方向都留出大于近裁剪面范围的间隙（按最大视野和最宽屏幕算）。
- **相机缓动让开阔处的位置也滞后** → 缓动的是偏移的绝对值，而偏移本身随俯仰变化。只缓动障碍物造成的那部分。

### 流程
- **没看到已有的路线图就自己定义了 M1** → 会话开始时本地 `main` 落后于远端，路线图又分散在文档、milestone 和 issue 三处。开工前先 fetch 最新的 `main`；进度只记在 `docs/ROADMAP.md` 一处。
- **子 agent 的工作树缺少最新提交** → 工作树是从 `main` 建的，分支上还没合并的提交不在里面。启动后要核对工作树的提交，或者先把分支合进 `main`。
- **审查者用 `git diff` 看未提交的改动，中途被快照提交清空** → 给审查者一个固定的对比基准（提交号），不要依赖“未提交”这个状态。
- **容器重启时，只在本地分支上的工作差点丢掉** → 两个工作包做完后只提交在工作树的本地分支上，没有推送；容器重启时后台任务全部中断，如果文件系统被重置就没了。每个工作包完成一个阶段就合进工作分支并推送，哪怕是半成品快照。
- **并行做的两个包合并后才发现对不上** → 两个包各自测试都通过，但真正的客户端第一次接上真正的服务器就暴露了 3 个问题。并行开发之后要留一步端到端的集成和验证，不能只看各自的测试。
- **token 花费偏高** → 每个模块“实现 + 两名审查 + 修复”全部用最高思考强度，约 100～200 万 token。之后改为默认 `high`、每模块一名审查者，难题再升级。

## M2.3 形状系统时踩的坑

格式同上：现象 → 原因 / 解法方向。

### 测试与校验
- **倾斜的木筏上的楼梯测试一直通过，藏住了移动校验的缺陷** → 场景本该是一条漂着的木筏。部分方块被当成整格算质量时，木筏载不动楼梯，歪着倾斜 23°，身体被斜着的踏面推离楼梯的对角线，正好避开了“沿对角线走，阶梯路径过不去”的缺陷。船改成按真实形状算质量后，木筏只倾斜约 9°，身体正走在对角线上，测试失败。场景要明确搭成想测的样子（木筏够大、几乎不倾斜），倾斜单独做成有名字的用例；测试里断言它真的走到了要测的情形（例如每条上报都落在对角线上）。别的模块一改测试就变结果时，先查场景是不是还是原来那个场景。
- **为楼梯放宽的余量，在普通的墙上也起作用** → 竖直上限加“√2 × 水平位移”时，条件只有“上报以着地结束”，一条上报于是能横移 4 格跳上 8 格高的墙。加了“两处之间阶梯路径走得通”之后，跳到墙沿上的上报仍然算走得通，因为阶梯路径最后竖直的那一段没有上限。为老实玩家放宽的每一处余量，都要有一个只有老实的情形才满足的条件，并且拿作弊的上报去测：墙、墙沿、台地、桅杆。
- **对照实现和被测的代码一起错** → 光照的对照实现和引擎照同一段文字写，“只看自己这一侧的面”这个误解让两边一致地漏光（上下半砖交替铺的屋顶下面天空光是 14）。对照之外还要有一个不从同一段文字推出来的检查，比如在半格网格上从露天处泛洪，泛洪不到的地方必须是暗的。
- **几个包各自通过，合在一起失败** → 并行做的包各自的测试都绿，合并后别的包里十个测试失败：测试写死了旧契约的字面值（随机生成的八分格编号到 255；用 `toEqual` 比较没有新字段的目标），或者按固定的毫秒数等一个校正。契约一变，合并之前就要找出所有按旧契约写死字面值的测试；测试等事件要按条件等，不按固定时间。

### 形状与查询
- **问格子中心，只回答了一个八分格** → 格子中心正好落在三个中间平面上，按半开区间它属于八分格 7。倒水的检查只问“格子中心被船体排开了吗”，被船体排开一部分的世界格子就判错了。关于一整格的问题要问它的每个八分格（8 个八分格的中心），不能拿格子中心代表整格。
- **封顶成常数的容差，结构体一倾斜就不成立** → 判断站在什么上面时，为了排除贴着的墙，把脚印四周内缩一个最多 0.05 格的量。倾斜的结构体上，墙脚沿着网格自己的“上”伸到脚印下面：倾斜约 2° 时，站在 0.005 格宽的踏面上的老实身体被判成没站住；倾斜约 10° 以上 0.05 又不够，倾斜 20.6° 的木筏上能声称站着、贴着桅杆往上爬 18 格。和几何有关的容差要按几何算（这里是倾斜的正切乘探测的深度），不能封顶成整格世界里定的常数；要在几种倾斜角下测。
- **每 tick 的代码传双部件格子的整格内容，每次调用都分配** → 双部件格子的整格内容 ≥ 2³¹，在 V8 里是堆上的数，传给没被内联的函数每次装箱 16 字节。每 tick 运行的代码（碰撞、光照、瞄准的复查）只读 `getCell` 和 `getPart2`（都小于 2²⁵）再查表，整格内容只给一次性的工作用；点查询只收整数坐标，原因相同。
- **把格子值加宽时，旧代码会静默截断** → 71 处代码把格子当 16 位存，其中几处本地拷贝会悄悄丢掉高位。设一根绊线：带“还有第二部件”标志、却没带第二部件的值，在 `setCell`、编解码、按形状或按接触判断的函数里都抛错（只读 id 的判断不查，它们读到的第一部件本来就对）。漏改的地方第一次碰到双部件格子就报错，而不是丢数据。

### 流程
- **一条过渡规则让七个包同时开工** → 形状系统要改七八个互相依赖的系统。先定了一条过渡规则：还没改造的系统把有部件的格子当成第一部件材质的整格方块（这正是它们不改代码时的行为），被瞄准的格子从射线起就用完整的值，方块事件只带第一部件。这样按任何顺序合并都不出错，七个包同时做。大的重构先找这样一条“没改的部分照旧成立”的规则，再分包。
- **在繁忙的机器上交替跑来比性能，报告里的表仍然是错的** → 同一份代码两次运行就差 1.1～1.7 倍；负载很高时交替运行新旧代码比中位数，结果也随负载漂（同一个液体探针 1.13～1.36 倍）。一份实现报告把基准提交量得慢了三成，得出“这个包只占 1.08 倍”，实际是 1.35 倍。vitest 下和打包后的构建也不同：同一个收集循环不被内联时是 M1 的 1.12～1.21 倍，打包后 1.04～1.06 倍。性能的定数要在空闲的机器上、新旧代码交替运行、每边多次取中位数，热循环在打包后的构建里再量一遍；报告里的表附上原始数据，由另一个人复现之后才用。
